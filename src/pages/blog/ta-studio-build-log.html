THE BUILD LOG

Background / Inspo

Why this project

Every semester the UT CS office staffs every class with TAs and UGCAs (undergrad course assistants). The person who runs it has done it since fall 2021, and he was doing it across an old web app called taproc, two copies of a spreadsheet, ChatGPT and his inbox.

A project advisor posted the idea in Slack with a product doc and a fake dataset. I picked it up because it was a real person with a real, messy process, and I wanted to see if I could replace it.

The Original Idea

What I set out to build

One page that runs the whole staffing cycle. Students keep applying in taproc. My tool reads that data and never writes back. Everything after the application happens in the new tool.

Students apply in taproc, the old app
↓
TA Studio reads that data (and never writes back)
↓
Professors rank applicants and request hours
↓
The office places people and checks for conflicts
↓
Offers go out and students accept or decline
↓
HR draft that shows what changed since the last one

AI Model + Tools

What I'm working with

Using Claude as my AI pair the whole way through.

  • One self-contained HTML page is the whole app. It runs in the browser with no server, so I could show it to anyone anywhere.
  • Node.js + Cheerio is the scraper that reads taproc's pages and pulls data out of the HTML.
  • Python runs the build script that stitches the template and data into one index.html.
  • A fake taproc is a copy of the old site with the same markup and fake data, so I can test without touching real students.
  • Claude API powers the Ask box that points staff to the right feature.
  • jsdom runs the tests, clicking through the built page without opening a browser.

Setup

Step 1 · Starting from scratch

The advisor had already built a demo, but his app repo was private and I could never get into it. So instead of waiting, I built a standalone single page seeded from his fake dataset. It had a dashboard, faculty ranking, an assignment workspace that shows when several professors want the same student, versioned publishing and an audit log.

The first interview with the office lead gave us one rule before I wrote anything. The tool never scores or auto matches candidates. He said taproc's "best match" suggestion is unreliable and he ignores it, and the product doc banned it too.

Note · The calendar

Undergrad applications opened three days after that first interview. That meant this semester could only be watched, not automated, so every version was built to be ready for the next cycle.

The Weekly Loop

Step 2 · Build, walk through, repeat

Every version answered the last conversation. I would build, we would walk through it together, and he would tell me what was wrong. It went through six versions in about seven weeks. A lot of the "bugs" were really me not knowing how the office works yet.

Bug #1 · A role that doesn't exist

The dataset had a role called Proctor, so I built screens for it.

The Fix

Proctor is just the old name for UGCA. The real roles are TA, AI (assistant instructor, a grad student teaching a class) and UGCA. I also switched UGCAs to hours instead of full or half time, because that's how HR enters them in Workday.

Bug #2 · Matching people by name

Grad students with research jobs (GRAs) get taken out of the pool, so the tool cross checks the GRA lists. I was matching on names. Grant admins misspell names and format lists differently, so real people slipped through.

The Fix

Match on EID first. Anyone who only matches by name goes in a separate list for a second look.

Bug #3 · "It's busy"

In the Oct 27 walkthrough the demo felt overwhelming next to taproc's plain pages. Labels like "Faculty windows" and "Not opened" didn't mean anything to him.

The Fix

I restyled it to look like taproc, with the same burnt orange band, tabs and row colors (yellow must place, blue other support, red excluded). Then I numbered the workflow tabs, added page tips and built the Ask box in Step 7.

Legacy Data

Step 3 · Reading an app I'm not allowed to touch

CS IT would not give anyone else access to taproc's server. No database, no API, no code. The only thing I could see was what a signed in browser sees. So I copied the HTML of taproc's pages by hand, scrubbed the names, and wrote down what every page and row color meant.

Then I built a fake taproc with the same markup and fake data. That gave the scraper something safe to run against, and the tests still use it.

Rules the scraper follows

Some taproc pages have buttons that email students or remove them from the pool. So the scraper only sends GET requests, never submits a form, and never follows a link that isn't a view. It never stores the CSRF token. Grades make this data confidential under FERPA, so real names and EIDs stay in git ignored local files and the tests only use fake people.

The First Real Pull

Step 4 · Four guesses and one real fix

On Oct 27 I ran the scraper against the real taproc for the first time, with the office lead in the room. I copied my session cookie from the browser into the command line pull and ran it.

Bug #4 · Zero of everything

It read 0 courses and 0 applicants. Every time.

Guess 1 · The login page

The login wasn't taproc's own page like I assumed. It's the shared UTCS sign in page. So I copied the whole cookie header instead of one cookie. Still zero.

Guess 2 · Cloudflare

Maybe the site blocks clients that don't look like a browser. I added an optional LEGACY_UA setting to send my browser's user agent. Still zero.

Guess 3 · The redirect loop

The applicants page kept redirecting back to itself because the session refreshes on each request. I made the pull follow same site redirects with the refreshed cookie, up to 5, GET only. Still zero.

Guess 4 · Look at what came back

I added a probe that saves the raw pages to my Mac. Every single one said the same thing.

Access denied. You must be logged in

The UTCS sign in ties the session to the browser that made it. A copied cookie is never going to work, no matter what else I send with it.

The Real Fix

Stop trying to look like a browser and just run inside one. I wrote browser-dump.js, a script you paste into the DevTools console of a tab that's already signed in to taproc. It sends GET requests from inside that tab, saves the pages, and downloads one file. Then the parsing happens offline on my Mac.

scraper/browser-dump.js (trimmed)async function get(path) {
  if (path in pages) return pages[path];
  const url = BASE + path;
  if (new URL(url).origin !== location.origin)
    throw new Error('refused other host');
  await sleep(120);
  const r = await fetch(url, { method: 'GET',
    credentials: 'same-origin', redirect: 'follow',
    cache: 'no-store' });
  const t = await r.text();
  if (/You must be logged in|type="password"/i.test(t))
    throw new Error('Not signed in: ' + path);
  pages[path] = t; return t;
}

credentials: 'same-origin' is the whole trick. The browser attaches its own valid session to every request, so the sign in never sees a stranger.

It refuses to talk to any other host, and it waits 120 ms between requests so it doesn't hammer taproc.

If it lands on a login page it stops with an error. Before this, a failed pull would quietly write an empty file, which looked like "nobody applied."

# in a signed in taproc tab, open DevTools, go to Console
# paste scraper/browser-dump.js and press Enter
# it downloads ~/Downloads/legacy-dump.json, then on the Mac
npm run sync:dump

Real Data

Step 5 · Nobody was linked to a class

The first walkthrough on real data was Nov 3. Every applicant showed up, but none of them were connected to the classes they asked for.

Bug #5 · 0 of 103

The pull linked 0 of 103 TA applicants and 0 of 246 UGCA applicants to any class.

The Fix (that wasn't)

taproc stores class requests as free text names, so I assumed the names just didn't match. I loosened the name matching. Nothing changed, because that was the wrong diagnosis.

The Real Fix

taproc's applicant page is an empty shell. After the page opens, its own JavaScript loads the application, including the requested classes, from a separate address. My scraper saved the page before that happened, so the data was never in the HTML at all.

// The applicant page is an empty shell. admin.js loads the
// application (with the requested classes) from /ajax/ta_record/{id}
const shell = await get('/admin/applicant/' + id);
const m = shell.match(/id="record"[^>]*data-id="(\d+)"/);
await get('/ajax/ta_record/' + (m ? m[1] : id));

Now the pull reads the shell, grabs the record id, reads the endpoint the page itself calls, and merges the two. I updated the fake taproc to serve pages the same way, and old dumps now warn that they're missing this data. After the fix it linked 103 of 109 TA applicants and 250 of 253 UGCA applicants.

What I'd do differently

Open the Network tab before writing a parser. The request with all the data was sitting right there the whole time.

Hardening

Step 6 · My Mac fell asleep mid pull

On Nov 10 I ran a full pull to build a real sample for a presentation.

Bug #6 · Missing applications

The pull lost 1 TA and 3 UGCA applications, and the console was full of these.

ERR_NETWORK_IO_SUSPENDED
ERR_TIMED_OUT
ERR_ADDRESS_INVALID

The Mac slept or the Wi-Fi dropped in the middle of the run, and the script skipped any applicant whose request failed.

The Fix 
for (let k = 0; k < 5; k++) {
  if (k) await sleep([2000, 5000, 10000, 20000][k - 1]);
  const ac = new AbortController();
  const to = setTimeout(() => ac.abort(), 30000);
  try { r = await fetch(url, { ...opts, signal: ac.signal });
        t = await r.text(); }
  catch (e) { r = null; }
  finally { clearTimeout(to); }
  if (r && (r.ok || (r.status < 500 && r.status !== 429))) break;
}

Each request now gives up after 30 seconds and retries 4 times, waiting 2, 5, 10 and then 20 seconds. And I run caffeinate -d during a pull so the Mac stays awake.

Bug #7 · Applicants with no class at all

taproc lets grad students apply without picking any classes, so they stayed unlinked.

The Fix

The office lead already handles these by looking up the student's supervisor. So the tool does the same thing. It suggests them to every TA class their supervisor teaches, and it handles the messy ways professor names are typed, like "LAST, F" and "Dr. X."

Bug #8 · A column I should never read

taproc hides columns instead of leaving them out. One table carried an SSN yes or no column in hidden HTML.

The Fix

The pull stopped reading that field completely. If the tool doesn't need it, it doesn't touch it.

Usability

Step 7 · An Ask box instead of a manual

The office lead said he got lost finding things. Instead of writing a long manual, I put an Ask box on every admin page. You type what you want to do, and Claude matches it against a fixed list of everything TA Studio and taproc can do.

It either takes you to the right tab, tells you the taproc menu path, or gives you a workaround and saves the question as a feature request for me. Claude only ever sees the question and that list, never student data. A scheduled task emails me every morning when there are new requests, so the missing features come to me instead of me guessing.

THE FINAL BUILD

Final Product

What the finished project looks like

The whole staffing cycle works on real data in one page. Course setup and CSV import, the real applicant pull, the GRA cross check by EID, faculty ranking windows, the assignment workspace with conflict checks, publishing with a student offer page, HR drafts that show what changed, and a UGCA roster that replaces the spreadsheet. The history import covers 984 past TAs and UGCAs, so new versus returning is automatic.

It isn't in production yet. CS IT will host it on taproc's server, and they need to choose a read only path into taproc first, either a read only database user or a GET only JSON API. Until then, real data comes in through the in tab pull.

"Built an all-in-one TA tool handling faculty rankings, TA assignments, HR exports, and email" the resume line this project earned

The Clean Path

How I'd do it again with zero snags

This is what I'd tell myself on day one, with every fix baked in.

1. Learn the job before building screens

Get the real roles, the real HR columns and the pay rules from the person who does the work. Most of my early bugs were wrong assumptions about the office, not code.

2. Treat the old app as read only from day one

GET only, no forms, no stored tokens, and only read the fields you need. Fake data in every test.

3. Build a fake copy of the old site

Same markup, fake people. The scraper, the app and the tests can all run without real student data.

4. Don't fight a browser bound sign in

If a copied cookie gets "Access denied," pull from inside a signed in tab and parse offline.

# signed in taproc tab, DevTools Console
# paste scraper/browser-dump.js, press Enter
npm run sync:dump

5. Open the Network tab first

If the page is an empty shell, read the endpoint its own JavaScript calls.

6. Expect the network to drop

Timeouts, retries with growing waits, and caffeinate -d during long pulls.

7. Ship a way to ask

An Ask box that routes people and collects what's missing beats a manual nobody reads.
