THE BUILD LOG

Background / Inspo

Why this project

This started as a totally different idea. My family runs a small obesity medicine clinic, and I first asked how to do medical billing for a practice like that. Their outside biller drops claims, and the doctor reconciles two lists by hand.

I ran a poll in a doctors' Facebook group asking clinic owners which one task they would hand off. Billing turned out to need a track record and certification before anyone trusts you with their revenue. Marketing is low risk for a clinic to try, so I pivoted. Then I narrowed it again, because all in one clinic marketing is crowded. The doctor said local Facebook groups brought in the most patients, and almost nobody helps clinics with that.

The Original Idea

What I set out to build

Done for you marketing that takes the clinic owner about 5 minutes a week. The app learns the clinic, drafts a week of posts, makes branded images, and publishes them once the clinic approves.

Clinic profile, the "brand brain" (services, doctors, voice, colors)
↓
AI drafts a week of posts and captions
↓
Branded slide images are rendered for each post
↓
Clinic approves, or it auto approves 12 hours before posting
↓  every 15 minutes
Scheduler publishes to Instagram and Facebook through the Meta Graph API
The one rule

The app stores no patient information, ever. No names, no contact details, no health details. New patient reports are counts only. That rule killed a lot of features (texting patients, missed call text back) but it keeps the whole thing out of HIPAA territory.

AI Model + Tools

What I'm working with

Using Claude as my AI pair the whole way through. Inside the app, the writing is done by Claude Sonnet 5.5.

  • Next.js 16 runs the whole web app, both the screens and the server code.
  • Postgres on Neon + Prisma stores clinics, posts and settings. Migrations run on every deploy so I never run them by hand.
  • Vercel hosts it and redeploys on every push to GitHub.
  • Satori + Sharp turn a layout into a JPEG slide image, since Instagram only accepts JPEG.
  • Meta Graph API is how an app publishes to Instagram and a Facebook Page.
  • GitHub Actions calls the scheduler every 15 minutes, because Vercel's free crons only run once a day.

First Deploy

Step 1 · The AI broke the day it went live

The first real version had logins, an admin console, the clinic profile, weekly AI drafts, branded slides, approval, the scheduler and the Meta connection. I put it on GitHub, Neon and Vercel and connected the Anthropic key.

Note · Why it worked locally

Claude built and tested everything against mock servers, because it couldn't reach the real Facebook, Instagram or Anthropic APIs from where it was working. So the real problems only showed up once I deployed.

Bug #1 · 400 on every AI call 
400 error: tool_choice type tool/any not supported

Every AI call forced a tool so the answer would come back as clean JSON. Sonnet 5.5 rejects forced tool use, so nothing could be drafted.

The Fix

Switch every AI call to structured outputs. You hand the model a JSON schema and it has to answer in that shape.

lib/ai.ts (trimmed)res = await c.messages.create({
  model: MODEL,
  max_tokens: opts.maxTokens ?? 8000,
  system: opts.system,
  output_config: {
    effort: opts.effort ?? "medium",
    format: { type: "json_schema", schema: strictSchema(opts.schema) },
  },
  messages: [{ role: "user", content }],
});

Later I also stopped showing raw API errors to the clinic. A 401 with a wall of JSON now becomes "The AI isn't set up correctly on this server," and a busy API becomes "Try again in a minute."

Deploy Mistakes

Step 2 · Three ways to break your own deploy

Bug #2 · The zip that ate my layout 
Can't resolve '../auth-actions'

Early fixes came to me as zip files that I unzipped and pushed. One got unzipped into the wrong folder and replaced the main app/layout.tsx with the clinic layout.

The Fix

Restored the root layout and put the clinic layout back where it belongs. After that, every change went straight to GitHub instead of through zip files.

Bug #3 · Slide previews broken on Vercel

The images that show each post wouldn't load once deployed, even though they worked locally.

The Fix (three causes at once)

The image links were full URLs built from an APP_URL setting, so a wrong setting broke every preview. In the app they're relative now, and only publishing uses full links because Meta has to fetch them. Fonts were read from disk while the app was running, and deploys don't always include those files, so they're built into the code now. And the native image module (@resvg/resvg-js) was unreliable on Vercel, so slides render with Sharp only. If a preview still fails it shows a Try again button and logs why.

Bug #4 · The doctor kept seeing old bugs

I'd fix something and she'd still see it.

The Fix

Her invite link pointed to a per deploy Vercel URL. Those are frozen copies of one build and never update. I sent her the production domain and set APP_URL to it too, since Meta pulls post images from that address.

⚠️ Slide layout gotcha

Satori counts padding as extra width and height, so my slides came out the wrong size. Absolutely positioned inner boxes with exact sizes fixed it, and text boxes need width: 100% or they won't wrap.

Meta

Step 3 · Connecting to Facebook and Instagram

This was a chain of separate problems, and each one was hiding the next.

Bug #5 · Nobody could connect

While a Meta app is in Development mode, only people with a role on the app can connect.

The Fix

Added the doctor as a Tester. She accepts the invite at developers.facebook.com/requests. App Review would remove this step, but it needs Business Verification, which needs a registered company and can take weeks.

Bug #6 · Wrong account

It connected to her personal Facebook instead of the clinic's Page.

The Fix

Disconnect in Settings, remove the app under Business integrations in Facebook, then reconnect and pick only the clinic's Page and Instagram.

Bug #7 · Domain error 
The domain of this URL isn't included in the app's domains
The Fix

The domain has to be in App Domains, and the exact callback address has to be in Valid OAuth Redirect URIs. You also have to start the connect flow from that same domain, because the login state cookie belongs to one domain.

https://<your-domain>/api/meta/callback
Bug #8 · "No Instagram business account" 
Couldn't publish: No Instagram business account is linked to this Facebook Page

Every post failed with this, even though the clinic's Page clearly shows Instagram connected. I checked it live. The Page's linked accounts showed the clinic's Instagram, and Business Suite showed the right portfolio owning both.

The Real Cause

Under the doctor's Business integrations, the app had only 2 of the 6 permissions it asks for. Meta silently drops any permission that isn't added to the app's Use cases in the developer dashboard. Without the Instagram permissions, Meta hides the Instagram account from the app, and the app only checks for Instagram once, right when someone connects.

The fix, in this order.

  • In Meta for Developers, add pages_manage_posts, pages_read_engagement, instagram_basic and instagram_content_publish under Use cases.
  • Remove the app from the doctor's Business integrations. Otherwise Meta reuses the old, incomplete grant.
  • Reconnect from the production domain, tick the clinic's Page, its Instagram and the right business portfolio, and leave every permission on.
Note · Test mode

With META_DRY_RUN=true, posts show as published but nothing is actually sent. It has to be false to go live. Very easy to forget.

Inspiration

Step 4 · Inspiration that didn't inspire (three rounds)

Clinics can save posts they like as inspiration, with what they like and don't like about each one. But new posts never changed. The only thing that ever made a visible difference was a doctor headshot added way earlier.

Round 1 · It only changed the words

Inspiration was only sent to one feature, and only as text.

The Fix

The AI now reads each saved screenshot's style and keeps a Do and Don't style guide built from all the notes. Every way of making a post follows it.

Round 2 · Every slide was the same template

The style guide could change the wording but never the look. Also, drafts that already existed were never rewritten.

The Fix

Six look settings picked from inspiration (background, alignment, headline size, decoration, capitals and highlighted words), a new list slide, live previews, and a "Refresh my drafts" button. Image links also include when the clinic last changed, so a new look shows right away instead of a cached image.

Round 3 · The real cause

The look picker copied the saved look into React state when it loaded. After inspiration changed the look on the server, the picker still showed the old one. Tapping "Save this look" then saved the old look back and locked it as hand picked, which stopped inspiration from ever changing it again.

The Real Fix

The picker now resyncs whenever the saved look changes. I didn't fix it by remounting the component with a key, because that wipes the "saved" message. I also send the three newest screenshots as images and weight them most, so one new post isn't outvoted by text notes from 20 older ones. And the save message now says exactly what changed, or that the look is locked.

Timeouts

Step 5 · Refresh my drafts never finished

Bug #9 · The page never reloaded

Rewriting 11 drafts in one server request took about 30 seconds per post with the real AI. It ran past the time limit and the page just hung.

The Fix

The catch is that Next.js server actions run one at a time per user. So even splitting the work up wouldn't run it in parallel. The browser now rewrites three drafts at a time through a small route handler, and shows "Rewriting 4 of 11" while it goes.

app/app/refresh-drafts.tsx (trimmed)const queue = [...ids];
const worker = async () => {
  while (queue.length) {
    const id = queue.shift()!;
    const r = await refreshOne(id);
    if (r.ok) done++;
    else failed++;
    setProgress({ done: done + failed,
                  total: ids.length });
  }
};
await Promise.all([worker(), worker(), worker()]);

Three workers share one queue of draft ids. Each one grabs the next id, rewrites that draft, and goes back for more until the queue is empty.

Each draft is its own short request, so nothing hits the time limit. If some fail, it says how many and you tap again to retry just those.

Code Review

Step 6 · The small bugs a review caught

I did a full code review before more clinics came on. These were found and fixed in one pull request.

  • A post set for any time between midnight and 1 am got scheduled at 9 am instead.
  • Skip, edit, rewrite and Post now could touch a post while it was publishing, which could post it twice.
  • A failed Post now was logged as published.
  • The menu had 13 entries. Now it's 7 with tabs, plus a "Find or ask anything" search box.
THE FINAL BUILD

Final Product

What the finished project looks like

Each clinic gets a login where it approves next week's posts, saves inspiration, adds photos, gets help joining local community groups, drafts safe review replies and sees what brought in new patients. Posts are AI drafted in the clinic's voice, turned into branded slides, auto approved 12 hours out if nobody objects (never for health claims), and published to Instagram and Facebook on a schedule. I'm now piloting it with three clinics.

"Developed a multi-tenant app where an LLM drafts a week of on-brand posts and captions for small clinics" the resume line this project earned

The Clean Path

How I'd do it again with zero snags

This is what I'd set up on day one so I never hit these errors.

1. Use structured outputs from the start

Don't force tool use to get JSON. Pass a JSON schema as the output format, and turn API errors into messages a clinic can act on.

2. Ship through git, never zip files

Push every change to GitHub and let Vercel deploy it.

3. Make images deploy proof

Relative image links in the app, full links only for Meta, fonts built into the code, Sharp for rendering, and a version number in every image link so caches never show an old look.

4. Only ever share the production domain

Set APP_URL to it too, since Meta fetches images from there.

5. Set up Meta before connecting anyone

Add every permission under Use cases, add the domain to App Domains, add the callback to Valid OAuth Redirect URIs, and add each clinic owner as a Tester. Then connect from the production domain, pick the Page, the Instagram account and the right portfolio, and set META_DRY_RUN=false.

6. Never copy server data into local state without resyncing

If a component copies a prop into useState, update it when the prop changes, or it will save stale data back.

7. Split slow AI work into small requests

About 30 seconds per post adds up fast. Run a few at a time from the browser through a route handler, with progress and retry.
