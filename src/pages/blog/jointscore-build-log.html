THE BUILD LOG

Background / Inspo

Why this project

I spent a year doing hip and knee replacement outcomes research at UT Southwestern. Outcomes like that are tracked with short patient surveys. KOOS, JR is the knee one (7 questions) and HOOS, JR is the hip one (6 questions). I wanted an iPhone app that gives either survey, scores it, and keeps every score on the phone. Then I wanted it to be able to read the questions out loud and fill in the answers by itself.

The Original Idea

What I set out to build

Enter the patient, pick the knee or hip survey, answer it by hand or by voice, and get the official score. Save it on the phone and track it over time.

Patient name, optional MRN, side, surgery date and collection date
↓
Manual entry, or Agent mode where the app reads each question and listens
↓
Raw sum converted to the 0 to 100 score with the official HSS tables
↓
Saved on the phone, with a trend and change from the pre-op baseline
↓
PDF reports and CSV export

AI Model + Tools

What I'm working with

Using Claude as my AI pair the whole way through.

  • SwiftUI builds the screens of the iPhone app.
  • SwiftData stores every score on the phone. Nothing goes to a server.
  • Xcode is where the app actually gets built and run on my iPhone.
  • AVSpeechSynthesizer is Apple's built in text to speech.
  • SFSpeechRecognizer is Apple's speech recognition, on the device where the phone supports it.
  • Kokoro-82M is an open source voice model (Apache-2.0) I used to pre-record a natural voice.
Note · The weird part

Claude never compiled or ran this app. iPhone apps only build in Xcode on a Mac, and Claude was writing code in a Linux workspace where it could only check the syntax. So every round went the same way. Claude writes the change, I build it in Xcode, and I paste the red errors back.

Prototype

Step 1 · A web app first

The first version was a web app with New score, Records and Guide tabs. It saved records to a cloud store tied to my Claude account. I wanted the data on my device instead, so it switched to saving in the browser with PDF reports.

That still wasn't right. Browser storage can get wiped with website data, and it can't go on the App Store. So the same weekend I asked for the real thing, a native iPhone app.

Going Native

Step 2 · First build in Xcode

Claude wrote the app as 8 Swift files with a step by step Xcode README. I made a new Xcode project, dropped the files in and hit run.

Bug #1 · No UIKit 
Reports.swift: No such module 'UIKit'

UIKit is the iPhone's UI library. Xcode had made a multiplatform project (iPhone, Mac and Vision Pro) and was building for "My Mac," where UIKit doesn't exist.

The Fix

Limit the target to iPhone and iPad and pick my iPhone as the run destination, not My Mac. The original project settings got backed up first as project.pbxproj.backup.

Bug #2 · Only the newest iPhones

The new project defaulted to a minimum of iOS 26.5, which would lock out most phones.

The Fix

Lowered it to iOS 17.0. That's the lowest it can go, because SwiftData needs 17.

Note · Developer Mode

I asked if turning on Developer Mode makes my phone easier to hack. There's no meaningful remote risk, and you need it while using a free Apple ID. The catch is that apps installed that way expire after 7 days. Hitting run in Xcode again renews it without losing records.

Agent Mode

Step 3 · Making it listen

Agent mode is the part I was most excited about. The clinician hands the phone to the patient, the app reads each question out loud, listens, and fills the answer in on the form. I didn't want an AI model guessing what patients meant, so the answers go through a rule based phrase table that's predictable and testable.

Bug #3 · Six errors at once 
Type 'VoiceInterviewer' does not conform to protocol 'ObservableObject'
Initializer 'init(wrappedValue:)' is not available ...   (x5)

This Xcode project makes every file import what it uses. @Published comes from Combine, and the file never imported Combine.

The Fix

One line.

VoiceInterviewer.swift (top of file)import SwiftUI
import Combine   // @Published lives here

Since the earlier UIKit error came from the same strict rule, I also added import Symbols to the screen with the pulsing mic icon before it could break.

Bug #4 · My fixes kept disappearing

The files were fixed on disk, but Xcode kept showing the old versions. When it asked, I picked "Keep Xcode Version," which wrote the old code right back over the fix.

The Fix

Pick Read From Disk (or Revert), or quit and reopen Xcode. Never "Keep Xcode Version." To check it updated, look at the first lines of the changed files.

Bug #5 · "Kind of satisfied"

The parser read "kind of satisfied" as Satisfied, because "satisfied" matched last in the phrase table.

The Fix

This one got caught in a test run of the parser before it ever shipped. The phrase rules now map it to Somewhat satisfied. The parser also uses the last answer mentioned, so "mild, no actually moderate" becomes moderate. It refuses to guess on "not severe," asks again after an unclear reply, and leaves the question blank after 3 tries.

Bug #6 · It heard itself

The phone's speaker fed back into the mic, so the app could transcribe its own question as an answer.

The Fix

The app never listens while it's talking. It speaks, stops, then listens.

Bug #7 · Silent on mute

With the ring switch on silent, the voice didn't play at all.

The Fix 
try AVAudioSession.sharedInstance()
    .setCategory(.playback, mode: .spokenAudio)

The playback category tells iOS this audio is the point of the app, so it plays even with the switch on silent.

⚠️ The icon that wouldn't change

iOS caches app icons. To see a new one, delete the app and run it again. That also deletes the test records, so don't do it with real data on there.

The Voice Saga

Step 4 · A voice that doesn't sound sad

v1 · Apple's default voice. It worked, but it sounded robotic.

v2 · The best Apple voice on the phone. The app picks the highest quality English voice installed, speaks sentence by sentence with short pauses, and varies its confirmations ("Okay, moderate." "Got it, mild."). It also got a voice picker and a Preview button. It was better, but the big improvement needed each user to download a 100 to 400 MB Premium voice in Settings. I still thought it sounded sad and robotic.

v3 · An open source human sounding voice. It had to be free, allowed for commercial use, and small enough for a phone.

OptionLicenseVerdict
Kokoro-82MApache-2.0Picked. Best small open model, free for commercial use
ChatterboxMITMore expressive, too heavy for a phone
Orpheus, DiaOpenToo large for a phone
Fish Audio S2 ProPaid commercial licenseNot free
F5-TTS, HiggsNon-commercialCan't be sold

Running Kokoro on the phone would add about 80 MB and need iOS 18. But everything the agent says is fixed text. There are 7 knee questions, 6 hip questions, a few prompts, the satisfaction question and some confirmations. So instead of generating speech on the phone, every sentence got rendered once on a computer and shipped as audio.

  • Two voices, a female default and a male option, trimmed and compressed to about 2.8 MB total.
  • Each clip is named after a hash of its sentence, like f_<hash>.m4a. Before speaking, the app hashes the sentence and plays the matching file.
  • No match means Apple's voice reads that line, so nothing ever breaks.
⚠️ Rule for changing any wording

If the app's text changes, the clip has to be regenerated with make_clips.py. Otherwise that line quietly falls back to the Apple voice.

THE FINAL BUILD

Final Product

What the finished project looks like

A native iPhone app that gives and scores KOOS, JR and HOOS, JR, works out the time point from the dates, and asks a separate satisfaction question after surgery that never touches the score. Every record stays on the phone with search, edit, trends and change from baseline. It exports a one visit survey report PDF, a multi visit patient summary, an all patients PDF and a CSV. Agent mode interviews the patient in a natural recorded voice.

The natural voice update still needs its first build on a real iPhone, and TestFlight is the next step after the paid Apple Developer account.

Note · Permission before selling

HSS calls these surveys free to use, but says they can't be altered without written permission, and a voice version is different from the paper form. So I'm asking HSS for written permission before anything goes on the App Store.

The Clean Path

How I'd do it again with zero snags

This is the setup that would have skipped every error I hit.

1. Set up the Xcode project right

Make an iOS app project, not multiplatform, and don't pick SwiftData as the storage option (the app sets up its own). Delete Xcode's template ContentView before adding the files. Set the minimum to iOS 17 and pick your iPhone, not My Mac, as the run destination.

2. Import what every file uses

UIKit for colors and PDFs, Combine anywhere you use @Published, Symbols for animated icons.

3. Always Read From Disk

When files change outside Xcode, never pick "Keep Xcode Version."

4. Design the voice loop first

Never listen while speaking, use the playback audio session so it works on silent, and parse answers with rules you can test.

5. Pre-record anything with fixed wording

If the app only ever says set sentences, render them once with an open model and look them up by hash, with the system voice as a fallback.

6. Get permission early

If you build on a published survey, ask the owner before you sell it.
