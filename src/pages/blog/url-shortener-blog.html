The Original Idea

What I set out to build

Client hits your server → app asks Redis "are you rate-limited?" → if no, app asks Redis "do you have this URL cached?" → if not, fall back to Postgres → send the result back, caching it in Redis on the way.

Bug #1 — Wrong JDK

The Fix

Bug #2 — No DataSource

Fixing the first error led me straight into a second one:

***************************
APPLICATION FAILED TO START
***************************

Description:
Failed to configure a DataSource: 'url' attribute is not specified
and no embedded datasource could be configured.

Reason: Failed to determine a suitable driver class

Basically what is happening here is that Spring Boot sees the Postgres driver + JPA dependencies in our classpath (already written in our pom.xml from the dependency selections) and assumes "this app wants a database." But with no URL/credentials given, there is nothing to connect to, so it fails with the error. Claude assumed there were no DB dependencies.

The Fix (part 1)

Get Postgres up and running locally, listening on port 5432:

docker run --name shortener-db -e POSTGRES_PASSWORD=pass -e POSTGRES_DB=shortener -p 5432:5432 -d postgres

And since Spring Boot doesn't know how to connect to a database without the connection details, we filled application.properties with them:

spring.datasource.url=jdbc:postgresql://localhost:5432/shortener
spring.datasource.username=postgres
spring.datasource.password=pass
spring.jpa.hibernate.ddl-auto=update
Bug #2, still — Same error??

Yet even after this fix I had the same error. Pasting the error into Claude, it said it's likely Java isn't connecting to our Docker container at all and is hitting a different Postgres server also listening on port 5432. So we ran:

lsof -i :5432

Which led us to find that there was in fact a native Postgres process running directly on my Mac that was stealing the Java app's connection.

The Real Fix

Move our Docker container to port 5433. To do this we recreated the container:

docker rm -f shortener-db
docker run --name shortener-db -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=pass -e POSTGRES_DB=shortener -p 5433:5432 -d postgres

Then updated the line in application.properties:

spring.datasource.url=jdbc:postgresql://localhost:5433/shortener

In summary: our main error was a port conflict between a local install and a container.

Database Layer

Step 4 — The Url entity

Url.javapackage com.yourname.shortener;

import jakarta.persistence.*;
import lombok.Data;
import java.time.LocalDateTime;

@Entity
@Data
public class Url {

}

@Entity tells Spring "this class maps to a database table," where each field is a column.

@Id + @GeneratedValue means the database auto-assigns IDs.

@Data (Lombok) auto-generates getters/setters.

Database Layer

Step 5 — The repository (the thing that talks to the database)

UrlRepository.javapackage com.yourname.shortener;

import org.springframework.data.jpa.repository.JpaRepository;
import java.util.Optional;

public interface UrlRepository extends JpaRepository<Url, Long> {
    Optional<Url> findByShortCode(String shortCode);
}

You write an interface (general template) without an implementation, and Spring will generate the actual save/find/delete logic for you at runtime.

findByShortCode works just because of the method name: Spring reads the method name at startup, matches its words against the entity's fields, and uses that to build a real database query automatically, so findByShortCode gets turned into SELECT where shortCode = ? without you ever writing the logic yourself.

The Core

Step 6 — The controller: creating short links and using them

UrlController.javapackage com.yourname.shortener;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import java.util.UUID;

@RestController
public class UrlController {
    private final UrlRepository repo;

    public UrlController(UrlRepository repo) {
        this.repo = repo;
    }

    @PostMapping("/shorten")
    public String shorten(@RequestBody ShortenRequest request) {
        Url url = new Url();
        url.setLongUrl(request.longUrl());
        url.setShortCode(UUID.randomUUID().toString().substring(0, 6));
        repo.save(url);
        return url.getShortCode();
    }

    @GetMapping("/{shortCode}")
    public ResponseEntity<Void> redirect(@PathVariable String shortCode) {
        Url url = repo.findByShortCode(shortCode)
            .orElseThrow(() -> new RuntimeException("Not found"));
        return ResponseEntity.status(HttpStatus.FOUND)
            .header("Location", url.getLongUrl())
            .build();
    }

    public record ShortenRequest(String longUrl) {}
}

@RequestBody tells Spring "take the JSON from the request and turn it into a ShortenRequest object."

Endpoint 1: POST /shorten — create a short link

Store the long URL in a new Url object and generate a random code by making a UUID (long random string), chopping the first 6 chars (short code), and sending it back to the requester, then saving the object to the database using the repository.

Endpoint 2: GET /{shortCode} — use a short link

If someone visits yoursite.com/(shortcode), @PathVariable grabs the shortCode and looks up the database for a Url row with that code. If nothing is found, it returns an error. Otherwise:

return ResponseEntity.status(HttpStatus.FOUND)
    .header("Location", url.getLongUrl())
    .build();

This builds an HTTP response with status code 302 (Found) and sets a Location header to the original long URL. Browsers understand "302 + Location header" means go here instead The browser instantly jumps to the long URL. No page is shown, it just redirects.

Caching

Step 7 — Adding Redis caching

Next we add the Redis dependency from Spring's Redis client library so Java code can talk to Redis the same way as Postgres. Added this in the pom.xml in the <dependencies> block:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>

Then point Spring Boot at Redis by adding this to application.properties:

spring.data.redis.host=localhost
spring.data.redis.port=6380

Then in UrlController.java the redirect logic becomes cache-aware:

UrlController.java (updated redirect)private final StringRedisTemplate redis;

public UrlController(UrlRepository repo, StringRedisTemplate redis) {
    this.repo = repo;
    this.redis = redis;
}

@GetMapping("/{shortCode}")
public ResponseEntity<Void> redirect(@PathVariable String shortCode) {
    String cacheKey = "url:" + shortCode;

    // 1. Check Redis first
    String cachedUrl = redis.opsForValue().get(cacheKey);
    if (cachedUrl != null) {
        System.out.println("CACHE HIT for " + shortCode);
        return ResponseEntity.status(HttpStatus.FOUND).header("Location", cachedUrl).build();
    }

    // 2. Fall back to Postgres
    System.out.println("CACHE MISS for " + shortCode + " — checking Postgres");
    Url url = repo.findByShortCode(shortCode)
        .orElseThrow(() -> new RuntimeException("Not found"));

    // 3. Write into Redis for next time (expires in 1 hour)
    redis.opsForValue().set(cacheKey, url.getLongUrl(), 1, TimeUnit.HOURS);
    return ResponseEntity.status(HttpStatus.FOUND).header("Location", url.getLongUrl()).build();
}

StringRedisTemplate is Spring's built-in tool for storing and reading key-value pairs in Redis. When a search is made, redirect creates a cacheKey and first checks for it in the cached temporary Redis database if it has been called recently, and if not, it then pulls the request from the Postgres database and writes it into Redis for next time with the cacheKey, with an auto-expiration period.

Rate Limiting

Step 8 — The rate limiter

Now we use Redis to track request counts, store that count for a certain time so that multiple servers can use it, then reset after the data automatically expires after n seconds.

The way we do this is using a filter, a piece of code that runs on every request to check if the client's IP counter is below the rate limit. This is a simplified fixed-window counter, not a "true" token bucket, backed by Redis.

RateLimitFilter.javapackage com.yourname.shortener;

import jakarta.servlet.*;
import jakarta.servlet.http.*;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;
import java.io.IOException;
import java.util.concurrent.TimeUnit;

@Component
public class RateLimitFilter implements Filter {
    private final StringRedisTemplate redis;

    public RateLimitFilter(StringRedisTemplate redis) {
        this.redis = redis;
    }

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest request = (HttpServletRequest) req;
        HttpServletResponse response = (HttpServletResponse) res;

        String key = "rate:" + request.getRemoteAddr();
        Long count = redis.opsForValue().increment(key);

        if (count == 1) {
            redis.expire(key, 60, TimeUnit.SECONDS);
        }

        if (count > 10) {
            response.setStatus(429);
            return; // blocks the request
        }

        chain.doFilter(req, res);
    }
}

@Component tells Spring to run and manage it automatically so that you don't have to wire it into every controller; it applies globally.

redis.opsForValue().increment(key) atomically adds 1.

if (count == 1) happens on the first request — that's when we set the expiration.

Returning early (without calling chain.doFilter) is what actually blocks the request, so the controller code never runs.

What is atomic vs racing?

When you have two requests, instead of:

Request A: reads value → 5
Request B: reads value → 5 (B read before A wrote back)
Request A: computes 5 + 1 = 6, writes 6
Request B: computes 5 + 1 = 6, writes 6
Final value: 6

Even though two requests happened, the counter only went up by one. Atomic does:

Request A: increment() → Redis does read+write as one indivisible step → returns 6
Request B: increment() → Redis does read+write as one indivisible step → returns 7
Final value: 7

Testing the limiter

To test, we hammer the same endpoint more than 10 times quickly:

for i in {1..15}; do curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/ping; done

200 will be printed 10 times, then 429 for the rest, meaning you've reached your limit and requests are blocked.

Step 10 — Deploying to Railway

Now it's time to deploy. I pushed my latest code to GitHub:

I'm using Railway to host. Go to railway.app → sign up with GitHub → New Project → Deploy from GitHub repo → select your shortener repo. Railway auto-detects it's a Maven/Spring Boot app and builds it.

Then we add the Postgres and Redis databases. Railway automatically generates connection credentials, and you don't need to manage Docker containers here.

Note — I did this wrong first

What I do in this next step is NOT the way I am supposed to do it. Claude had originally guided me this way, but I ran into errors and learned more about the conventions. I did want to be true to my process and log it. You will see later in the blog the correct way to do it, and I will point it out as well.

In application.properties, I updated it to read environment variables:

spring.datasource.url=${DATABASE_URL}
spring.datasource.username=${DATABASE_USERNAME}
spring.datasource.password=${DATABASE_PASSWORD}
spring.jpa.hibernate.ddl-auto=update
spring.data.redis.host=${REDISHOST}
spring.data.redis.port=${REDISPORT}
spring.data.redis.password=${REDISPASSWORD}

Both database info and Redis info were found by clicking on the respective database box and going to the Variables tab. I then committed and pushed this change (Railway auto-redeploys on every push to your connected branch).

Good practice

You should never commit passwords/confidential info publicly, put it in .gitignore if needed.

Bug — The shortener keeps crashing

All 3 services were online, however I noticed my shortener keeps crashing. The Railway logs showed a "no datasource configured" error, meaning Railway needs the databases explicitly referenced as variables in the app service's own Variables tab.

Quick explanation as to why it errors: there is a mismatch between Postgres's DATABASE_URL format and Spring Boot's respective spring.datasource.url JDBC format. Therefore we'll just build the JDBC URL from the individual pieces the Postgres database generates on Railway.

The Fix — the correct way

First, delete all the info lines in application.properties, leaving just these two lines:

spring.application.name=shortener
spring.jpa.hibernate.ddl-auto=update

Then add these variables in the app's Variables tab in Railway:

Variable nameValue
SPRING_DATASOURCE_URLjdbc:postgresql://${{Postgres.PGHOST}}:${{Postgres.PGPORT}}/${{Postgres.PGDATABASE}}
SPRING_DATASOURCE_USERNAME${{Postgres.PGUSER}}
SPRING_DATASOURCE_PASSWORD${{Postgres.PGPASSWORD}}
SPRING_DATA_REDIS_HOST${{Redis.REDISHOST}}
SPRING_DATA_REDIS_PORT${{Redis.REDISPORT}}
SPRING_DATA_REDIS_PASSWORD${{Redis.REDISPASSWORD}}

And to fix the exposed password, I regenerated the passwords in Railway.

Finally, to test if it's working: find the URL in app service → Settings → Networking → Generate Domain, then run:

curl -i https://shortener-public-url/ping

Final Product

What the finished project looks like

A live, publicly deployed URL shortener: you POST a long URL to /shorten, it hands you back a 6-character code, and anyone who visits yourdomain/{code} gets instantly 302-redirected to the original link. Redis serves cached lookups so repeat hits never touch Postgres, and a Redis-backed rate limiter blocks any IP that sends more than the allowed requests per window with a 429. All of it runs on Railway with managed Postgres + Redis.

The Clean Path

How I'd replicate it with zero snags

This is the step-by-step that I found worked for me, with all the fixes baked in from the start, so you skip every error I hit.

1. Setup

Install Docker Desktop and Java 17+. Generate the skeleton on start.spring.io: Maven · Java · latest stable Spring Boot · Artifact: shortener · Java 17 · Dependencies: Spring Web, Spring Data JPA, PostgreSQL Driver, Lombok. In IntelliJ, before running anything, set the Project SDK and Language level to 17+ (File → Project Structure) so you don't hit the SDK 1.8 error.

2. Databases on non-default ports

Check what's already on the default ports first (lsof -i :5432) — a native Postgres install will silently steal your app's connection. Just start on 5433/6380 from the jump:

docker run --name shortener-db -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=pass -e POSTGRES_DB=shortener -p 5433:5432 -d postgres
docker run --name shortener-redis -p 6380:6379 -d redis

Then in application.properties:

spring.datasource.url=jdbc:postgresql://localhost:5433/shortener
spring.datasource.username=postgres
spring.datasource.password=pass
spring.jpa.hibernate.ddl-auto=update
spring.data.redis.host=localhost
spring.data.redis.port=6380

3. Build the app in this order

PingController.java (sanity check the server runs) → Url.java entity → UrlRepository.java → UrlController.java with both endpoints → add the spring-boot-starter-data-redis dependency → cache-aware redirect → RateLimitFilter.java. All the code is in the process log above; it works as-is once the ports are right.

4. Test each layer as you go

# server alive?
curl http://localhost:8080/ping

# cache working? (watch the IntelliJ CONSOLE tab, not the terminal)
curl -i http://localhost:8080/YOURCODE   # CACHE MISS, then CACHE HIT on repeat

# rate limiter working? 10x 200 then 429s
for i in {1..15}; do curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/ping; done

5. Load test with redirects disabled

hey follows 302s by default and will hammer the destination site instead of your server. Always pass -disable-redirects:

hey -n 2000 -c 50 -disable-redirects http://localhost:8080/$CODE

6. Deploy to Railway the right way

Push to GitHub → Railway → New Project → Deploy from GitHub repo → add Postgres + Redis services. Do not put connection details in application.properties, strip it down to just:

spring.application.name=shortener
spring.jpa.hibernate.ddl-auto=update

…and set the six SPRING_DATASOURCE_* / SPRING_DATA_REDIS_* variables in the app service's own Variables tab, building the JDBC URL from Railway's Postgres pieces (full table in the deployment step above). Never commit credentials; regenerate any password that ever touched a public repo. Generate a domain under Settings → Networking and curl -i https://your-url/ping to confirm it's live.
